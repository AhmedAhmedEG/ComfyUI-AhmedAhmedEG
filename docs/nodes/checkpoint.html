MiniMax H3 Load Take Checkpoint

Loads a complete saved take from a project’s server-side cache.

Checkpoints4 outputs

Use it when: Use it to resume or branch from an already completed clip.

In plain language

A take is one generated version of a shot. This loads a complete take saved in this pack’s server-side cache, including the compressed generation result needed by continuation workflows. It is not a diffusion-model loader.

Your first use: Choose the project ID, clip ID and take ID of a completed saved take. These IDs identify cache entries; they are not the friendly shot name. Use the outputs in a continuation graph. Importing a workflow JSON alone does not bring those cache files with it.

Connections

checkpoint → Master continuation
frames / audio → export nodes if you only want the saved media

A saved generated take, including its working state

A checkpoint here is a cached take from this pack, not a diffusion-model weight file. The node loads decoded frames, audio and the sampled H3 latent. Its continuation output also records project_id, clip_id and generation/take identity. Connect checkpoint to Master.continuation when deliberately continuing a selected result, or use the separate outputs for inspection/export.

project_id chooses the server-side project cache. clip_id chooses a shot within that project. take_id=latest loads the shot's current manifest entry. A specific take_id looks up the recorded take and verifies that it belongs to the requested shot. It does not search another project merely because an identically named file exists.

Change detection and completeness

For latest, IS_CHANGED tracks the cached latent file's modification time so a newer take can trigger reevaluation. A specific take uses that explicit identity. The loader requires readable latent, frames and audio; it raises an error for a missing/incomplete checkpoint. Loading a workflow JSON on another server cannot restore these files automatically.

Save the take identity when reproducibility matters. Latest is convenient during iteration, but it intentionally changes when another take becomes current. A saved-take selector and the Master’s validated flag are separate concepts: selection chooses a take; validation requests reuse only when effective inputs/fingerprints are compatible.

The checkpoint remains server-side tensor/cache state. A preview MP4 has neither the complete latent nor its continuation masks and cannot stand in for a checkpoint. Keep the cache when moving/restoring projects that depend on continuation.

Implementation: Checkpoint.load and IS_CHANGED, manifest/take storage.

Execution summary

  • latest selects the current take for clip_id. An explicit take UUID selects that historical generation from the manifest.
  • Loads the saved latent, decoded frames and audio. Fails if any required artifact is missing or unreadable.
  • Returns a continuation object plus separate media and latent outputs; it does not generate a new take.

How to use it

  1. Find the project ID, shot ID and optional take UUID in the Master’s saved-take tools.
  2. Enter those values and load the checkpoint.
  3. Connect checkpoint to another Master continuation input to branch or continue.

Settings and controls

Initial values come from the node’s declared UI schema. The starter can use different values. Required settings have widgets; they do not all require cables. Runtime model/sampler choices depend on your installation.

Limits and troubleshooting

  • Project and shot IDs are cache identifiers, not the shot’s display name.
  • Cache files must remain on the same server or be restored. Portable reference archives exclude heavy generated-take storage.
